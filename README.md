# Memit Demo 0.1

Backend: Java 21, Spring Boot 3.5, Maven Wrapper, Web, JPA, файловая H2, Java2D. Android и дизайн реализуются отдельно.

## Запуск (PowerShell)

Установите JDK 21 и задайте JAVA_HOME на каталог JDK. Первый запуск Wrapper требует интернет.

```powershell
cd backend
$env:JAVA_HOME = 'C:\path\to\jdk-21'
$env:Path = "$env:JAVA_HOME\bin;$env:Path"
.\mvnw.cmd test
.\mvnw.cmd spring-boot:run
```

Linux/macOS: `sh ./mvnw test` и `sh ./mvnw spring-boot:run` из backend.
Всегда запускайте из backend: `data/memit.mv.db` хранит БД, `uploads/` — JPEG. Оба каталога сохраняются после перезапуска; резервируйте вместе. Пользователи 1 (Аня), 2 (Максим) создаются без дубликатов. Последнее фото определяется по времени UTC и ID.

Поместите собственный лицензированный Impact в `backend/fonts/Impact.ttf`. Без него используется жирный SansSerif, в логах предупреждение. Шрифт не включён в репозиторий.

Проверка:
```powershell
curl.exe http://localhost:8080/api/health
curl.exe http://localhost:8080/api/users
curl.exe -F "file=@photo.jpg" -F "senderId=1" -F "recipientId=2" http://localhost:8080/api/photos
curl.exe "http://localhost:8080/api/photos/latest?userId=2"
curl.exe http://localhost:8080/api/photos/1/image -o received.jpg
```

Эмулятор Android: `http://10.0.2.2:8080`. Физический телефон: LAN IP компьютера, общая Wi-Fi сеть и доступ к порту 8080.

`ApiController` принимает запросы и отдаёт DTO; `ImageService` проверяет формат, выбирает текст/фильтр и рисует JPEG; `Photo` и `DemoUser` описывают таблицы; репозитории выполняют запросы JPA; `ApiErrors` формирует ошибки JSON. Текст и фильтр выбираются однократно, скачивание читает сохранённый файл. Пропорции сохраняются. EXIF-поворот не применяется: клиент должен отправлять пиксели с корректной ориентацией.

Отсутствуют авторизация, регистрация, push, сложные друзья, PostgreSQL, Redis, S3, Docker, платежи и награды. Это локальная демонстрация; ID передаются напрямую.

Контракт и Android: [API](docs/API.md).

Новые фото обрезаются по центру до квадрата 1:1 без растяжения (сторона равна меньшей стороне исходника). Текст равновероятно располагается сверху, в центре или снизу; позиция фиксируется в готовом JPEG. Старые фото не изменяются.

## Совместная проверка: телефон по USB + эмулятор

Один backend должен обслуживать оба устройства. Запустите его на том же компьютере, к которому подключены телефон и эмулятор Android Studio. Сервер должен оставаться включённым; после выключения компьютера виджет не сможет получить новые фото.

### Окно PowerShell №1: сервер

Вводите команды сверху вниз, по одной строке. Если приглашение имеет вид `>>`, нажмите Ctrl+C и начните ввод заново.

```powershell
cd C:\MyFolder\memit\memit\backend
$env:JAVA_HOME = 'C:\Users\sagae\.jdks\openjdk-22.0.1'
.\mvnw.cmd spring-boot:run
```

Показанный JDK 22 уже установлен на компьютере автора, проект компилируется для Java 21. На другом компьютере укажите свой путь к JDK 21+. Не указывайте каталог `bin`. Запускайте Wrapper из backend и обязательно передавайте команду: `test` или `spring-boot:run`. Запуск одного `mvnw.cmd` выдаст No goals specified. Остановить сервер: Ctrl+C. Для тестов сначала выполните `.\mvnw.cmd test`, дождитесь BUILD SUCCESS, затем запускайте сервер.

### Окно №2: подключение устройств

На телефоне включите режим разработчика и отладку по USB, подключите кабель с передачей данных и подтвердите разрешение отладки. В терминале Android Studio выполните:

```powershell
adb devices
adb -d reverse tcp:8080 tcp:8080
```

`-d` выбирает физический USB-телефон, даже когда одновременно работает эмулятор. При нескольких телефонах используйте `adb -s SERIAL reverse tcp:8080 tcp:8080`, заменив SERIAL значением из `adb devices`. Статус должен быть `device`; при `unauthorized` подтвердите запрос на телефоне. Если adb не найден, используйте полный путь к `adb.exe` из каталога Android SDK `platform-tools` (путь SDK виден в Android Studio). Пример стандартного расположения Windows:

```powershell
& "$env:LOCALAPPDATA\Android\Sdk\platform-tools\adb.exe" devices
& "$env:LOCALAPPDATA\Android\Sdk\platform-tools\adb.exe" -d reverse tcp:8080 tcp:8080
```

После переподключения телефона или перезапуска adb повторите reverse. USB сам по себе не создаёт этот маршрут. Для этого способа общая Wi-Fi сеть не нужна.

### Какой адрес задать в Android-приложении

| Клиент | Базовый URL |
|---|---|
| PowerShell/браузер на компьютере сервера | `http://localhost:8080/` |
| Android Studio Emulator на компьютере сервера | `http://10.0.2.2:8080/` |
| USB-телефон после adb reverse | `http://127.0.0.1:8080/` |
| Телефон или другой компьютер в общей LAN | `http://<LAN-IP-сервера>:8080/` |

BASE_URL задаётся Android-разработчиком в настройке Retrofit/OkHttp, а не в настройках телефона. Например: `const val BASE_URL = "http://127.0.0.1:8080/"`. Для Retrofit оставляйте завершающий `/`. До появления переключателя окружений можно собрать приложение для телефона с одним адресом, установить его, затем сменить адрес и запустить сборку на эмуляторе. Установленная на телефон сборка сохранит прежний адрес.

Приложение и виджет должны читать один источник настройки адреса. `localhost` внутри устройства означает само устройство. `10.0.2.2` ведёт к компьютеру этого эмулятора, а не к компьютеру коллеги. Если сервер у другого участника, используйте его LAN-IP (`ipconfig` на сервере), общую сеть и разрешённый входящий TCP 8080 в брандмауэре для частной сети. Не отключайте брандмауэр целиком. Гостевая Wi-Fi сеть может изолировать устройства.

Разрешение INTERNET и debug-настройка cleartext HTTP описаны в [API.md](docs/API.md). Если в проекте уже используется networkSecurityConfig, согласуйте разрешение HTTP с его debug-конфигурацией. Выполняйте сетевые запросы вне главного потока, с таймаутами и обработкой ошибок.

Проверьте в браузере каждого устройства адрес BASE_URL + `api/health`. Ожидается `{"status":"UP"}`. Затем проверяйте приложение. Если браузер работает, а приложение нет — проверьте адрес сборки, INTERNET, cleartext и логи Android.

### Роли устройств и сценарий защиты

| Устройство | Владелец | Отправка | Получение |
|---|---|---|---|
| Телефон | Аня, ID 1 | senderId=1, recipientId=2 | latest?userId=1 |
| Эмулятор | Максим, ID 2 | senderId=2, recipientId=1 | latest?userId=2 |

ID владельца — настройка демоприложения, входа в аккаунт пока нет. Отправьте снимок с телефона, обновите виджет Максима в эмуляторе, затем проверьте обратное направление. Для камеры эмулятора нужна настроенная виртуальная камера/веб-камера; основной сценарий CameraX сначала проверяйте на телефоне.

Для проверки без Android во втором PowerShell:

```powershell
curl.exe http://localhost:8080/api/health
# Аня -> Максим
curl.exe -F "file=@C:\Users\sagae\Pictures\avaWinter.png" -F "senderId=1" -F "recipientId=2" http://localhost:8080/api/photos
curl.exe "http://localhost:8080/api/photos/latest?userId=2"
# Максим -> Аня
curl.exe -F "file=@C:\Users\sagae\Pictures\avaWinter.png" -F "senderId=2" -F "recipientId=1" http://localhost:8080/api/photos
curl.exe "http://localhost:8080/api/photos/latest?userId=1"
```

Замените путь фото своим. Возьмите imageUrl из JSON и добавьте адрес сервера: например, `/api/photos/3/image` -> `http://localhost:8080/api/photos/3/image` в браузере ПК. ID фото — поле `id`, а не senderId/recipientId.

## Памятка разработчику Android-виджета

Виджет — часть Android-приложения, backend специально для него менять не нужно. Выберите стандартный AppWidgetProvider/RemoteViews либо Jetpack Glance с учётом проекта команды. Это план интеграции: код виджета в этом репозитории пока не реализован.

1. Сохраните ID владельца и BASE_URL локально, чтобы виджет мог прочитать их после пересоздания процесса. Если поддерживаются разные владельцы для разных экземпляров, храните настройки по appWidgetId.
2. При добавлении виджета и ручном обновлении запросите `GET /api/photos/latest?userId=<владелец>`. Это входящие фото владельца, а не фото, отправленные им.
3. Из ответа возьмите id и imageUrl. Соедините URL корректно: база `http://host:8080/` + путь `/api/photos/3/image` должны дать `http://host:8080/api/photos/3/image`. Не вставляйте localhost жёстко в код загрузки картинки.
4. Скачайте JPEG вне главного потока, уменьшите Bitmap до размера отображения и обновите виджет. Не передавайте многомегапиксельный Bitmap через RemoteViews. Сервер уже обрезал изображение 1:1 и нанёс текст/фильтр; повторно ничего рисовать не нужно. Показывайте весь квадрат, чтобы не обрезать надпись по краям.
5. Кэшируйте последнее успешное изображение и ID на диске: виджет должен сохранять картинку при отсутствии сети или остановленном сервере. Если id не изменился и кэш есть, повторно скачивать JPEG не обязательно.
6. 404 при отсутствии входящих фото — пустое состояние «Пока нет мемов»; ошибка сети/500 — сохранить прошлое фото и дать повторить обновление. При смене владельца не показывайте кэш другого пользователя.
7. Добавьте явное действие «Обновить». Для защиты оно позволяет получить фото после отправки с другого устройства. Отправка сама по себе не будит приложение получателя: push в Demo отсутствует.
8. Сетевую работу выполняйте через подходящий фоновый механизм, например Worker; не держите длительный сетевой запрос в onUpdate/BroadcastReceiver. После загрузки обновляйте соответствующий экземпляр виджета.

Системный `updatePeriodMillis` не поддерживает интервал меньше 30 минут. Периодический WorkManager имеет минимальный интервал 15 минут, и точное время запуска не гарантирует. Поэтому периодическое обновление не подходит для мгновенного показа на защите: используйте ручное обновление. Не делайте бесконечный цикл опроса каждую секунду в фоне.

### Samsung, Xiaomi и Google Pixel

Backend/API и формат картинки одинаковы для всех трёх. Отдельный сервер или отдельная реализация виджета для каждой марки не требуются. Но проверять нужно конкретный телефон, версию Android и лаунчер:

- Сетка рабочего стола, отступы, размеры и изменение размеров виджета отличаются. Не рассчитывайте на фиксированное число пикселей; проверьте минимальный размер, увеличение и читаемость текста.
- Фоновая работа зависит от Android, прошивки производителя и пользовательских настроек батареи. Даже Pixel не гарантирует обновление в точную секунду. На Samsung/Xiaomi названия и поведение настроек могут различаться между версиями; универсальной инструкции по меню нет.
- Если фоновые обновления задерживаются, проверьте ограничения батареи для Memit на конкретном телефоне и логи Worker. Для демонстрации используйте явное обновление; не требуйте отключения всех системных ограничений как условие работы.
- Проверьте добавление виджета долгим нажатием на рабочий стол, изменение размера, обновление с открытым и закрытым приложением, отсутствие сети, повторное добавление и восстановление после перезапуска. Эмулятор не заменяет проверку на реальном телефоне.

Официальные источники: [сеть эмулятора](https://developer.android.com/studio/run/emulator-networking-address), [adb reverse](https://developer.android.com/develop/ui/views/layout/webapps/access-local-server), [обновление виджетов](https://developer.android.com/develop/ui/views/appwidgets/advanced), [периодический WorkManager](https://developer.android.com/develop/background-work/background-tasks/persistent/getting-started/define-work), [размеры виджетов](https://developer.android.com/develop/ui/views/appwidgets/layouts), [ограничения фоновых задач](https://developer.android.com/develop/background-work/background-tasks/bg-work-restrictions).

## Обновляется ли фото в виджете само сейчас?

Нет: текущий backend только сохраняет фото и отвечает на запросы. Он не отправляет уведомление получателю. Android-виджет ещё должен быть реализован; само наличие нового фото на сервере не меняет изображение на рабочем столе.

Для Demo 0.1 FCM не обязателен. Разработчик виджета реализует кнопку «Обновить»: по нажатию запрашивает latest, скачивает новый JPEG и обновляет виджет. Обновление при добавлении виджета или открытии приложения также нужно явно реализовать на Android. Это рекомендуемый сценарий защиты.

Автоматическое обновление без FCM возможно через периодические запросы Android (polling), но с задержкой и без точного расписания. WorkManager допускает период от 15 минут, updatePeriodMillis — от 30 минут; батарея и ограничения системы могут отложить выполнение. Для демонстрации получения фото сразу после отправки такой механизм не подходит. Обычный фоновый таймер не обеспечивает надёжную работу при закрытом приложении.

Если позже потребуется обновление вскоре после отправки при закрытом приложении, можно добавить FCM. Потребуются изменения обеих сторон: Android получает и передаёт токен устройства, backend хранит привязку токена к получателю и после сохранения фото отправляет событие, Android обрабатывает его и запускает загрузку/обновление виджета. Firebase используется для уведомления, а изображение по-прежнему скачивается с нашего backend. Доставка push и выполнение фоновой работы не гарантируются мгновенно. Если телефон использует USB reverse, backend доступен ему только пока работает это подключение; FCM не делает локальный сервер доступным через интернет. Для FCM нужен настроенный Firebase-проект и совместимое устройство/эмулятор с Google Play services.

FCM, хранение токенов, Android-получатель push и код виджета сейчас не реализованы. На данном этапе не подключаем Firebase ради демонстрации: используем явное обновление, а push оставляем отдельной будущей задачей.

### Кто реализует ручное обновление

Это задача разработчика Android-виджета. Изменения backend и отдельный эндпоинт «обновить виджет» не нужны: существующий API уже отдаёт последнее полученное фото.

Разработчик виджета должен:

1. Добавить кнопку/действие «Обновить» и обработчик на Android.
2. По нажатию запустить сетевую работу вне главного потока: `GET /api/photos/latest?userId=<ID владельца виджета>`.
3. Если пришло новое фото, скачать JPEG по imageUrl с тем же BASE_URL, сохранить его в локальный кэш и обновить отображение через AppWidgetManager/RemoteViews либо Glance. Если ID прежний и кэш есть, достаточно использовать кэш.
4. Обработать пустое состояние, таймаут и отсутствие сети, сохранить прошлую картинку при временной ошибке и завершить состояние загрузки. Не запускать несколько одинаковых обновлений одновременно.

Ответственность backend — сохранить мем и вернуть метаданные/JPEG. Ответственность Android-виджета — решить, когда запросить данные, выполнить запросы и показать картинку. Одно только нажатие кнопки без этой Android-логики ничего не обновит. Backend не управляет рабочим столом телефона напрямую. Ручное обновление виджета пока описано как задача для Android, а не реализовано в backend.
